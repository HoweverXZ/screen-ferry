# 0002. 线上格式手写编解码

- 状态：已采纳
- 日期：2026-11-01

## 背景

`ferry-proto` 需要一种二进制编码。候选方案：

| 方案 | 优点 | 缺点 |
|---|---|---|
| serde + postcard | 代码最少，派生即可 | 线上格式由 Rust 结构体的字段顺序隐式决定，改结构体就可能悄悄改了协议；引入 serde 派生宏，编译变慢 |
| Protocol Buffers | 跨语言，字段可选、可扩展 | 需要代码生成；可选字段让"合法消息"的边界变模糊；对键鼠这种小消息偏重 |
| 手写 | 格式完全显式，每个字节都有文档；没有依赖；容易做严格校验和 fuzz | 每条消息要多写十几行编解码代码 |

## 决策

手写编解码。规则如下：

- 小端定长整数，布尔只能是 0 或 1，字符串、字节串、列表带长度前缀，并且都有上限。
- 消息体必须被恰好读完。
- 每个值只有一种合法编码（规范编码）。

## 后果

- 协议文档（`docs/protocol.md`）与代码一一对应，线上格式不会因为重构结构体而意外改变。
- 测试里钉死了几条消息的完整字节；fuzz 和测试都检查"解码再编码得到相同字节"。
- 扩展靠新增消息类型加能力位，不靠给旧消息追加字段（见 `docs/protocol.md` 第 7 节）。
- 新增消息需要手写编解码，并在测试样例里补上；测试里有一个穷尽匹配，漏补时编译就会失败。
