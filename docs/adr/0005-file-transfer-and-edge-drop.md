# 0005. 文件传输与边缘投递

- 状态：已采纳（2026-11-01，维护者审阅交互原型后确认）
- 日期：2026-11-01

## 背景

键鼠共享之外，要能把文件从一台电脑交给另一台。最直接的想法是“拖着文件穿过屏幕边缘、在对方那里放下”，但这要在两台电脑之间交接一次正在进行的系统拖拽：取消本机的拖拽、在对方合成一次拖拽，按下、移动、松开的时机必须严丝合缝，Windows 甚至没有接口能知道别的程序正在拖文件。这是最容易出错、也最难做稳的部分。

## 决策

### 交互：边缘投递

文件始终在**本机**放下：

- 拖着文件靠近某条有邻居的边缘时，本机贴边滑出胶囊，对方同一位置也滑出接收胶囊。
- 放到胶囊上就发送。两边胶囊显示进度，任一端都能取消。
- 接收端收完后胶囊变成卡片：打开、在文件夹中显示，或把文件从卡片拖到任意文件夹。

两边用的都是系统标准的“接收拖放”和“发起拖放”，不交接拖拽本身。方向完全对称。胶囊是后台常驻进程的原生窗口，不是设置界面：拖文件时设置界面多半没开，另起进程也太慢、太占内存。

交互原型见设计画布“边缘投递胶囊交互原型”（2026-11-01）。

### 传输

- **文件连接**：每次传输单独开一条 TLS 连接（`channel = 4`），带上输入连接的会话号。大文件不会堵住剪贴板和键鼠，取消就是关掉这条连接，多个传输互不影响。
- **始终由客户端发起连接**：无论哪边发送，都由客户端连向服务端，被控的那台不需要开放入站端口。
- **控制消息走数据连接**：发送方发 `FileOffer`，接收方回 `FileAccept`，之后客户端打开文件连接；任一方都可以在数据连接上发 `FileCancel`。
- **能力位 `FILES`**：双方都声明才使用，新旧版本混用不会出错，不需要升级协议版本。
- **清单 + 顺序流式**：发送方先发清单（相对路径、类型、大小、修改时间），再按清单顺序逐个发送文件内容，每个文件结尾附 SHA-256。
- **断点续传**：接收方边收边写进缓存目录的 `partial/<传输号>/`，每校验完一个文件就记下进度。清单是顺序发送的，所以续传点只是“第几个文件、第几个字节”。会话中断后，发送方在下次连上时重新发出同一个传输号的 `FileOffer`，接收方据此接着收；清单变了就从头开始。
- **落地**：全部收完、校验通过后，才把顶层项目移到“下载”文件夹，重名时自动改名（`报告 (2).pdf`）。
- **自动接受**：只在已配对、证书固定的设备之间传输，发送又是用户主动拖放的，所以接收方不再弹窗确认。
- **安全**：
  - 清单里的路径只能是相对路径，不能含 `..`。
  - 文件名按两个系统的规则统一清洗：去掉 Windows 不允许的字符、保留设备名和结尾的点或空格。
  - 不跟随符号链接；跳过 `.DS_Store`、`Thumbs.db`。
  - 一次最多 10 万个条目、单个路径最多 1024 字节、最深 64 层。

### 分步实现

1. 传输核心：协议、发送与接收、续传、取消、落地。先用 `screenferry send <路径>` 交给正在运行的后台发送，便于实机验证。
2. 两台设备的边缘胶囊，含拖动中两端联动和接收端卡片。
3. 从卡片把文件拖到任意文件夹：可以拖动的区域由绘制描述标出，浮层用系统原生的拖动来源，由放下的地方决定移动还是复制。
4. 多设备布局：每个邻居一个胶囊，同一条边按段分开。

## 后果

- 文件传输与键鼠、剪贴板彼此独立，互不拖慢。
- 不能一个动作直接放进对方的某个文件夹，要先落到“下载”，再从卡片拖出去。换来的是两边都只用系统标准接口，稳定可靠。
- 接收位置暂时固定为“下载”。以后加设置项时，配置结构变化须按第 10 节递增 `schema_version`。
- 发送方的待续传任务只在内存里；后台重启后，未传完的任务需要重新拖一次，接收方的临时文件会在清单相同时继续使用。
